# 榴莲销售运营智能体：生产部署与运行说明

## 1. 当前实现范围

系统已由单机测试程序升级为“中央控制台 + Windows微信工作节点”结构。

- 中央控制台：保存客户、知识库、DeepSeek配置、会话、消息任务、订单和审计记录。
- Windows工作节点：操作本机已经登录的微信客户端，轮询已绑定会话，读取新消息，执行中央端排队的回复，并回写发送结果。
- 单个执行设备默认管理500条客户会话，最高可配置5000条。工作进程按批次轮询全部客户，批次之间使用持久化游标，确保后面的客户不会被长期跳过；一个微信窗口的界面读取和发送仍然必须串行。
- 多微信账号通过增加工作节点横向扩展。一个Windows交互式登录会话只绑定一个微信账号标识；中央控制台可以同时管理多台电脑和多个微信账号。

客户聊天数量不再固定为20条。多个微信登录账号仍需要分别运行在相互隔离的Windows交互式会话或执行设备中；单个微信客户端不能真正并行操作多个聊天窗口。

## 2. 底层消息流程

1. 工作节点从中央端取得本设备全部已启用会话绑定，默认最多500条，并使用持久化轮转游标分批扫描。
2. 节点按优先级逐个打开微信联系人，并严格核对聊天标题。
3. 首次扫描只记录当前可见消息基线，不处理旧消息。
4. 后续扫描只有在能找到可靠的历史消息锚点时，才把新增客户消息上传中央端。
5. 中央端用消息唯一编号去重，把消息写入会话，再走“知识库检索 → 业务边界判断 → DeepSeek组织语言或本地回退”。
6. 连续到达的多条客户消息会合并推进：同一会话尚未发送的旧自动回复会取消，只保留最新上下文生成的回复。
7. 回复进入消息任务队列。节点取得带租约的任务后，精确打开联系人、填写内容、点击发送并核对输入框是否清空。
8. 节点确认发送成功后，中央端才把销售消息写入会话；无法确认时记录失败，不自动重发。

这种结构保证GPT/Codex不参与生产运行。正式运行链路是：微信工作节点 → 中央控制台/知识库 → DeepSeek API → 消息任务 → 微信工作节点。

联系人来源问题走确定性规则，不交给DeepSeek自由生成。当前业务方确认默认来源为“公开网站的商户公开页面”；有具体网站或公开页面依据时，应写入联系人`source`和`source_basis`。文件名、工作表和行号只写入`import_provenance`，不得作为对外来源说明。来源发生冲突时暂停营销；明确要求不再联系时永久关闭该线索营销状态和会话自动回复。

## 3. 运行条件

中央端可以运行在一台固定Windows电脑。微信工作节点需要：

- 64位Windows，Python 3.11或3.12；
- 已安装并登录当前适配过的Windows微信客户端；
- 工作节点运行期间保持该Windows用户会话登录且桌面未锁定；
- 真实运行时把该Windows会话作为专用工作桌面，不要同时人工操作同一个微信窗口；需要人工接管时先在控制台暂停对应会话；
- 显示缩放、微信版本和窗口结构变更后，先重新做界面控件检查；
- 每个节点的`account_ref`使用稳定且唯一的业务标识，不能让两个在线节点同时操作同一个微信账号；
- 中央端和工作节点之间使用可信局域网、组网VPN，或由运维配置HTTPS反向代理。不要直接把8015端口暴露到公网。

图形界面RPA无法在Windows锁屏、远程桌面断开后切换到不可交互桌面、微信退出登录或安全验证页面中正常工作。系统会在这些情况下停止当前任务并记录异常。

微信获客不按华南、华东划分执行账号。每条任务保存线索导入时的实际地区快照，并在控制台单独显示；默认微信备注包含`{地区}`和`{店名}`。当前腾讯批准日上限为单账号150个，系统、控制台和RPA授权配置均按150封顶。申请提交成功只记录为“申请已发送”，客户通过或系统确认已是好友后才显示“添加成功”。

## 4. 中央端安装

在中央电脑的项目目录打开PowerShell：

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\install_windows.ps1
.\scripts\start_server.ps1
```

启动脚本会显示两项一次性配置：

- 节点注册口令：只用于新工作节点首次注册；
- 控制台管理口令：浏览器首次访问业务接口时输入。

默认监听`0.0.0.0:8015`。如只在本机使用：

```powershell
.\scripts\start_server.ps1 -HostAddress 127.0.0.1
```

生产启动使用Waitress多线程服务，不使用Flask开发服务器。中央端只运行一个进程；当前SQLite数据库不支持多个中央端进程同时写入。

## 5. 工作节点安装

把同一发布目录复制到每台微信工作电脑，然后执行：

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\install_windows.ps1 -WorkerOnly
```

节点身份不再要求手工填写JSON。首次启动会根据电脑名和当前Windows用户生成稳定节点编号，并自动创建`config\worker.json`。本机中央端直接运行即可自动注册：

```powershell
.\scripts\start_worker.ps1 -Once
```

连接另一台中央电脑时，首次启动把中央端地址、微信业务标识和一次性注册口令作为参数提供；程序注册成功后会加密保存节点令牌：

```powershell
.\scripts\start_worker.ps1 -Once `
  -ServerUrl 'http://192.168.1.100:8015' `
  -WechatAccount '销售微信01' `
  -BootstrapToken '中央端显示的一次性口令'
```

生成后的默认会话管理容量为500，`scan_batch_size`默认50。确有需要时可在部署配置中调整，后端允许的最大管理容量为5000。

先做不触碰微信的连接检查：

```powershell
.\scripts\start_worker.ps1 -Once
```

看到`dry_run_ready`表示节点注册和中央端连接正常。首次注册后，节点令牌会使用当前Windows用户的DPAPI加密保存，并从配置中删除明文注册口令。

## 6. 控制台绑定会话

1. 打开中央控制台的“执行设备与客户”。
2. 确认自动注册的执行设备已显示且容量正确。
3. 选择系统会话和工作节点。
4. 填写微信联系人显示名。该名称必须与微信聊天标题完全一致。
5. 选择是否自动回复，然后建立绑定。
6. 先让节点以真实模式完成一次基线扫描；基线建立不会发送任何消息。

未绑定的会话不能从会话工作台直接发送。工作台消息会先排队，只有节点确认成功后才进入正式会话记录。

## 7. 启用真实运行

确认微信已登录、会话绑定无误、知识库与DeepSeek连接正常后，在工作电脑执行：

```powershell
.\scripts\start_worker.ps1 -Live
```

不带`-Live`时永远是配置检查模式，不读取微信、不租出消息任务、不发送消息。

真实运行后重点观察：

- 节点状态是否持续在线；
- 活跃会话是否不超过节点容量；
- 是否出现“消息锚点丢失”“联系人标题不唯一”“安全提示”或“输入框未清空”；
- 消息任务是否由“排队 → 执行中 → 成功”，失败任务必须人工核对微信后再决定是否重新排队。

不要直接重试“租约过期”或“发送结果不确定”的任务，因为消息可能已经发到微信，只是中央端未收到回执。

## 8. 数据迁移和备份

在线备份使用SQLite备份接口：

```powershell
.\scripts\backup_data.ps1
```

备份文件默认写入`backups`目录。迁移中央端时：

1. 停止旧中央端；
2. 复制项目和最新数据库备份到新电脑；
3. 用备份替换`data\durian_agent.db`；
4. 在新电脑重新输入并测试DeepSeek API Key。

DeepSeek密钥使用中央电脑当前Windows用户的DPAPI加密，复制数据库后不能在另一台电脑直接解密，这是预期的安全行为。

工作节点配置中的节点令牌也绑定当前Windows用户。把节点配置复制到另一台电脑后，应清空`node_token_encrypted`，重新填写中央端节点注册口令并注册。

## 9. 安全和业务边界

- 中央业务接口在生产模式下必须携带管理口令；工作节点使用独立节点令牌，权限与控制台分离。
- DeepSeek API Key只保存在中央端，不下发到工作节点。
- 未命中知识库的低风险自然交流可以由DeepSeek结合对话上下文回答。
- 价格、运费、库存、发货时效、售后、赔付、合同、账期等业务事实仍受知识库边界约束；无法可靠回答时转人工。
- 平时使用已确认的公司和业务窗口身份沟通，不主动展示内部技术术语；客户直接询问自动化身份时必须如实说明账号由销售人员和服务系统共同维护，不得虚称真人或纯人工本人回复。
- 每次修改知识、话术、检索或对话状态逻辑后，必须运行版本化单轮和多轮语料回归；客户改口时采用最新明确表达覆盖旧值。
- 验证码、安全验证、操作频繁、联系人不唯一、消息方向不明确和发送结果不确定都采用失败关闭策略。
- 节点事件以JSONL写入`config\worker-events.jsonl`，超过10MB自动保留一份轮转日志；中央端同时保留审计记录。
- 客户明确停止沟通或转人工后，应在控制台停用该会话的自动回复。

## 10. 扩容建议

- 单设备默认管理500条客户会话，但图形界面操作是串行的。客户越多，完整轮询一次所需时间越长；生产环境应按可接受响应时间调节扫描批次，或增加执行设备分担客户。
- 多个微信账号：每个账号使用独立Windows交互式会话和工作节点，中央端汇总调度。
- 超过单机SQLite适用范围、需要多中央端高可用或大量并发写入时，应把数据库迁移到PostgreSQL并增加独立任务队列；当前版本未声称具备这一层能力。
- 每次升级微信客户端后先用测试联系人做一轮人工监督验证，再恢复正式自动回复。

## 11. 进销存与发货控制规程

正式业务必须按“采购建单 → 审批 → 到货登记 → 独立质检 → 可售库存 → 销售订单占库 → 确认收款 → 发货扣减 → 物流跟踪”的顺序执行。

- 采购单先保存为草稿，审批后才能收货；支持同一采购明细分批到货。
- 到货只能进入“待质检”区，不能在收货动作中直接变成可售。生产日期与到期日期同时填写时，到期日必须晚于生产日。
- 质检放行与拒收必须填写结论说明。已经形成质检结论的批次不能直接改写，避免覆盖历史判断。
- 可售量按“未过期可售现存量 - 生效销售占用量”计算。待质检、拒收和过期批次不参与销售占库。
- 销售占库采用整单原子策略：任一明细库存不足时整单不占用，避免形成无法履约的半张订单。批次分配按先到期先出库处理。
- 订单只有在“已付款”且存在有效占库时才允许发货。支持分批发货，每次发货按实际数量核销占用并写入独立运单。
- 运单号全局唯一；系统拒绝重复运单，避免重复扣库。物流状态可更新为已发出、运输中、已签收或物流异常。
- 库存流水只追加、不覆盖。采购入库、销售出库和盘点调整都保留业务来源、批次、数量、成本、操作时间和审计记录。
- 盘盈或盘亏必须先提交调整单，再单独批准。盘亏不得侵占已经锁给销售订单的库存。
- 旧版本商品库存首次迁移时进入`MIG-{SKU}`批次并标记为“待质检”，经实际盘点和质检放行后才可销售，系统不会把历史汇总数字直接当作可发库存。

当前物流模块负责发货单、承运商、运单号和状态控制，不会调用承运商下单、打印面单或查询真实轨迹。接入顺丰、京东物流等正式接口时，应在发货单创建成功前完成幂等下单，并把承运商返回的唯一业务号写回；接口超时且结果不确定时不得自动重试扣库。

退货和拒收返仓不能通过修改发货状态直接恢复库存。上线退货业务前，应增加独立销售退货单、验收入库和退款审批链路；在此之前只能由授权人员使用有凭证的库存调整流程处理，并在备注中关联原订单和运单。

首页会汇总低库存商品、待办采购单、可发货订单和物流异常。运营人员每天至少检查一次低库存与临期批次；财务确认收款、仓库发货、库存调整审批建议由不同人员负责。SQLite适用于当前单中央端规模，多中央端并发、高可用或大量仓库作业时应迁移PostgreSQL并引入独立任务队列。
